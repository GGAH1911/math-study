# Phase 3 — SSR 제거 → SPA 실행 체크리스트

> 2026-08-15 작성. 로드맵 [app-roadmap.md](app-roadmap.md) Phase 3 의 실행 계획.
> **일반론이 아니라 실측에서 나온 순서다.** 아래 숫자는 전부 이 레포를 직접 세어 얻었다.

## 왜 이 공사가 병목인가

전체 56항목 중 40개가 남았는데, 그중 **33개(Phase 5~8)가 Phase 3 뒤에 줄 서 있다.**
Phase 4 가 6/6 로 끝났는데도 앞으로 못 가는 게 그 증거다. 여기가 뚫려야 나머지가 움직인다.

## 실측 — 25개 페이지의 실제 성격

| 성격 | 개수 | 페이지 |
|---|---|---|
| **A. 마크다운 렌더** (`<Content>`) | **4** | `concepts/[...slug]` `problems/[...slug]` `mistakes/[slug]` `syntheses/[slug]` |
| **B. 콘텐츠 목록** (컬렉션만) | 8 | `concepts/index` `problems/index` `problems/units` `mistakes/index` `syntheses/index` `exam/random` `exam/round/[key]` `tools` |
| **C. 사용자 상태·DB** | 11 | `index` `atlas` `graph` `paths` `progress` `account` `settings` `log` `exam/index` `privacy` `terms` |
| **D. 인증** | 2 | `login` `signup` |

**이미 클라이언트에서 도는 것**: 17개 페이지가 Astro 아일랜드나 인라인 script 를 갖고 있다
(`concepts/[...slug]` 7개, `problems/[...slug]` 4개, `index` 4개…). **순수 SSR 은 8개뿐**이다.

→ ★**"25개를 전부 새로 만든다"가 아니다.** 상당수는 이미 클라이언트 로직을 갖고 있고,
  서버가 만들어주던 **껍데기(HTML)와 데이터 공급**만 바꾸면 된다. 공사 규모를 여기서 다시 잡았다.

**API 현황**: 엔드포인트 25개가 이미 있다. 다만 전부 **행위**용(`chat` `attempt` `progress`…)이고
**콘텐츠 목록**용은 하나도 없다 — B 그룹이 필요로 하는 게 그것이다.

## 순서를 이렇게 잡은 이유

A(마크다운)가 **가장 어렵고 가장 근본**이다. 링크 재작성이 빌드 시 `docs/` 전체를 훑어 만든
지도(`CONCEPT_LEAF_MAP`)를 쓰므로 **원리적으로 브라우저에서 못 돈다.** 그래서 A 를 먼저 풀지
않으면 B·C 를 아무리 옮겨도 핵심 화면(개념·기출)이 안 된다.

거꾸로 A 를 "빌드 시 선렌더"로 풀면 **부수 효과가 크다** — 콘텐츠가 정적 파일이 되므로
기기에 캐시할 수 있고, 그게 곧 **오프라인 동작**이다. 앱을 앱답게 만드는 게 이 한 수다.

      렌더 지표는 **정확히 일치**를 요구한다(링크처럼 20% 여유를 주면 수식 뭉텅이가 죽어도 통과한다).
      수식 감소·수식오류·FIG 미치환은 **차단 신호**다.
      · **기준선**: 18/22 라우트 200 · **수식 3,939 · 이미지 4,241 · 내부링크 12,695 · 오류 0**
      · ★첫 실행에서 바로 하나 배웠다: 문제 페이지의 수식이 0 이라 결함인 줄 알았는데,
        **기출 본문은 이미지**이고 수식 텍스트는 개념 문서 쪽이다(문제 `<img>`1 수식0 / 개념 `<img>`0 수식18).
        즉 A 그룹 4개는 **성격이 둘로 갈린다** — 수식형(concepts·syntheses) / 이미지형(problems·mistakes).
        선렌더 검증도 그에 맞춰 갈라야 한다.
      · ⚠️ `katex` 카운트는 **`class="katex`** 로 센다. 단순히 `katex` 문자열을 세면 인라인 CSS 의
        폰트 URL 473개가 섞여 들어와 항상 통과한다(실제로 처음에 그 함정을 봤다).

## 1단계 — 마크다운 선렌더 ★최대 난관

- [ ] **빌드 시 콘텐츠 → HTML+JSON 방출**
      · 4개 컬렉션(`concepts` `problems` `mistakes` `syntheses`)을 빌드 때 렌더해 파일로 굽는다
      · remark 4종 + rehype-katex 를 **그대로 재사용**한다 — 클라이언트 포팅이 아니다
      · 검증: 방출된 HTML 과 현재 SSR HTML 이 **같은 수의 `.katex`·내부링크**를 갖는가
- [ ] **링크 재작성 결과를 방출물에 굳힌다**
      · `CONCEPT_LEAF_MAP`/`CONCEPT_FULL_SET` 은 빌드 산물이므로 이 시점에 이미 적용돼 있다
      · 검증: 기존에 깨졌던 다중세그먼트 링크(2,583 문항분)가 방출물에서 정상인가
- [ ] **방출물 서빙 경로 결정** — `web/private/` 처럼 인증 뒤인가, 정적인가
      · ⚠️ 기출 본문은 **유료화 전제**다. `public/` 에 두면 게이팅이 조용히 꺼진다(2026-08-14 실사고)
      · 검증: 무인증 접근 → 302

## 2단계 — 콘텐츠 목록 API (B 그룹 8개)

- [ ] **목록 JSON 엔드포인트** — 컬렉션을 읽어 목록을 주는 API (지금 하나도 없다)
      · 검증: 응답 크기가 현재 SSR HTML 보다 **작아야 한다**(`problems/units` 5.5MB 가 기준)
- [ ] B 그룹 8개를 목록 API 소비로 전환

## 3단계 — 페이지 셸 이전 (A·C 그룹)

- [ ] **A 그룹 4개** — 1단계 방출물을 읽어 렌더
      · `syntheses/[slug]`(87줄) → `mistakes/[slug]`(53) → `concepts/[...slug]`(379) → `problems/[...slug]`(402)
      · ★뒤의 둘이 진짜 어렵다(아일랜드 7개·4개). 앞의 둘로 방식을 검증하고 들어간다
- [ ] **C 그룹 11개** — 사용자 상태는 이미 API 가 있다. 껍데기만 옮긴다
      · `privacy` `terms` `exam/index` 는 사실상 정적 — 여기서 시작한다

## 4단계 — 라우팅 + 인증 게이팅

- [ ] 클라이언트 라우터 도입 (페이지 전환이 서버 왕복 없이)

## 하지 말 것

- **25개를 한 번에 뒤집지 않는다.** 사장님이 매일 쓰는 웹이다. 페이지 단위로 옮기고 매번 잰다.
- **마크다운 파이프라인만 먼저 만들지 않는다.** 소비자(페이지)가 없으면 수요 없는 공급이다.
  1단계와 3단계 A 는 **붙여서** 간다.
- **remark 플러그인을 클라이언트로 포팅하려 하지 않는다.** 링크 재작성은 빌드 산물에 의존하므로
  브라우저에서 못 돈다. 선렌더가 유일한 길이다.
- **미들웨어 인증을 끄지 않는다.** 4단계 주의사항 참조.

## 열린 결정 (하다가 정해야 하는 것)

1. **방출물 형식** — HTML 통짜 vs 구조화 JSON. 전자가 쉽고 후자가 앱에서 유연하다.
   → 1단계 첫 컬렉션에서 둘 다 만들어 보고 정한다(되돌리기 싼 시점).
2. **라우터** — Astro 의 View Transitions 로 갈지 별도 라우터를 둘지.
   → 3단계까지 가서 페이지들이 어떤 모양이 됐는지 보고 정한다.
3. **오프라인 범위** — 콘텐츠만인가, 필기·진도까지인가. Phase 6 의 필기 지연 판정과 얽힌다.
