### 🔶 N3 진행 중 — 사업장 주소
조직 계정은 스토어에 **조직명·주소·연락처가 공개**된다. 현재 개인 주소라 **D-U-N-S 정정을 요청한 상태**.

★**D-U-N-S 만 고쳐도 끝나지 않는다** — 같은 주소가 여러 곳에 노출된다:
| 경로 | 공개되는 것 |
|---|---|
| Play Store 개발자 정보 | 조직명·주소·연락처 |
| App Store(조직 계정) | 동일 — **D-U-N-S 공유** |
| **통신판매업 신고** | 상호·주소·연락처가 공정위 사이트에서 조회 |
| 이용약관·개인정보처리방침 | 사업자 정보·보호책임자 연락처 기재 |

→ 실제 결정은 하나다: **사업장 주소를 무엇으로 할 것인가**(자택 vs 공유오피스·비상주).
정하면 D-U-N-S · Play · Apple · 통신판매업 · 약관이 한 번에 정리된다.
★순서 확인 필요 — D-U-N-S 는 사업자등록 정보에서 파생되므로 **등록증 소재지 → D-U-N-S → 스토어**
순서가 아니면 되돌아갈 수 있다.

**일정 영향은 제한적**: 내부·비공개 테스트는 **공개 스토어 페이지를 만들지 않는다**(포렌식 실측).
Phase 2~7 은 그대로 진행 가능하고, **주소가 공개되는 건 Phase 8 프로덕션 출시 시점**이다.
12명×14일이 빠진 자리를 이 리드타임이 대신하므로 같은 방식으로 다룬다 — 지금 시작해 Phase 8 전까지.

      | | 백필 전 | 백필 후 |
      |---|---|---|
      | chat_history jsonb 합계 | 1,006KB | **189KB** |
      | 최대 행 | 568KB | **46KB** |
      | 이미지 | 인라인 17장 | 본문 16개(중복 1건 통합) 517KB |

      검증(실물): ①백필 전 덤프의 이미지 해시 집합 == `chat_images` 본문 == messages 참조,

      ③같은 응답을 `POST` 로 되돌려도 jsonb 크기 동일·본문 중복 생성 0(멱등)

      ★백엔드는 지금 postgres `bytea` 다. **참조 형식과 `chat-images.ts` 의 외부 인터페이스는 그대로 두고**
      Phase 5 에서 R2 로 갈아끼운다 — 호출측이 저장소를 모르게 한 게 이 작업의 본체다.

      --import ./scripts/ts-resolve-hook.mjs scripts/backfill_chat_images.mjs` (기본 dry-run, `--apply` 로 반영)
- [x] **이미지 리사이즈 정책 재결정** ✅ 2026-08-13 — **결론: LLM 경로는 1568px 유지, 512px 는 표시 전용.**

      ★먼저 전제가 틀렸다: "표시용 512 다운스케일이 들어간다"는 맞지만 **LLM 은 512 를 본 적이 없다.**
      `image-utils.ts` 는 표시본(512, `DISPLAY_LONG_EDGE`)과 비전 타일(1568, `VISION_LONG_EDGE`)을
      따로 만들고, 전송은 타일로 간다. 판독 충실도는 처음부터 위험하지 않았다.

      진짜 질문은 **"다음 턴 이미지 창에 512 표시본으로 갈음해도 되는가"**(=타일을 영속화하지 않아도 되는가)였고,
      **안 된다**로 판명됐다. 기출 6장을 512·1568 두 크기로 전사시키고 라벨을 섞어 원본 이미지 기준으로 채점:

      | | 판독 오류 | 승 | 무 | 패 | PNG 평균 |
      |---|---|---|---|---|---|
      | **512px** | **10건** | 0 | 2 | 4 | 75KB |
      | **1568px** | **1건** | 4 | 2 | 0 | 181KB |

      512 가 낸 오류는 사소하지 않다 — 조건 누락(경우 5개 중 1개 통째로 빠짐), 사분면 오독,
      실선/점선 혼동, 축 오독. **채점기가 학생 풀이를 잘못 읽으면 제품이 틀린 지적을 한다.**
      저장량 2.4배는 이 차이 앞에서 싸다.

      ★**손글씨로도 확인 완료** (2026-08-13 저녁, 사장님이 아이패드로 직접 필기).
      스트로크를 각 해상도로 **벡터에서 직접** 렌더해(비트맵 확대가 아니라) 같은 하네스로 전사:

      | | 512px | 1568px | 원본 |
      |---|---|---|---|
      | 첫 항 | `q^{[?]}` | `9^{1/4}` | `9^{1/4}` |
      | 둘째 항 | `2x^{1/2}` | `2x^{1/4}` | `2x^{1/4}` |
      | 셋째 줄 | `3^{1/2}` | `3^{-1/2}` | `3^{-1/2}` |

      512 는 숫자 **9 를 `q` 로** 읽고, 지수 **1/4 을 1/2 로** 바꾸고, **음의 지수 부호를 지웠다.**
      인쇄체보다 오히려 더 나쁘다. 채점기가 이걸 보면 **맞은 풀이를 틀렸다고 한다** —
      제품의 코어가 그 지점에서 무너진다. 1568 은 세 줄 모두 정확.
      표본: `web/scripts/measure/handwriting_sample_20260813.png`

      재현: `web/scripts/measure/run_transcribe.py` → `judge.py` (심판은 claude 구독)
