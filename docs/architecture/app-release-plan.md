| 서버 역할 | 뺄 수 있나 | 이유 |
|---|---|---|
| 인증·회원관리 | 불가 | 원래 계획 |
| **LLM 프록시** | **불가** | 키를 앱에 넣으면 **바이너리에서 추출**된다 → 남의 크레딧으로 무단 사용. 사용량 계측·쿼터·차단도 서버에만 있다 |
| **구독 상태 검증** | **불가** | 클라이언트 판단은 위조 가능. 단 **구독관리 서비스(RevenueCat 류)로 대부분 외주 가능** |
| 콘텐츠 배포 | 가능 | CDN·오브젝트 스토리지로 이전 |
| 사용자 데이터 동기화 | 가능하나 **유지 결정** | 빼면 기기 변경 시 진도 소실 |

★**서버 역할을 줄여도 서버 비용은 거의 안 준다.** 비용을 정하는 건 기능 개수가 아니라 **가동 요건과
콘텐츠 트래픽**이다. 프록시는 I/O 대기라 CPU 를 거의 안 쓴다 → 작은 VPS 하나로 충분.
현재 tme 자가호스팅은 한계비용 0 이지만 **상용으로는 단일 장애점**.

## 🔨 스택과 무관하게 반드시 해야 하는 공사

**SSR 제거 → 클라이언트 렌더링 + JSON API.** 앱 프로젝트의 절반 이상을 차지한다.
- **사용자 대면 25개** 페이지 렌더링을 클라이언트로 (전체 45개 중 `/dev` 관리자 도구 20개는 SSR 유지·앱 미포함) 이동
- 인증 게이팅을 서버 미들웨어 → 앱 라우팅으로 이동
- 콘텐츠 조회를 서버 → **로컬 캐시**로 전환
- 세션 쿠키 → **access/refresh 토큰**(네이티브는 쿠키가 불편, Keychain/Keystore 보관)
- ★**동일출처 CSRF 검사 폐기 → Authorization 베어러 + CORS 허용 오리진 화이트리스트**
  (웹 도메인 · `capacitor://localhost` · `https://localhost`). `middleware.ts:83-88` 과
  `auth.ts:124` 를 함께 손본다. Capacitor 앱 오리진은 영영 불일치라 이 공사 없이는 앱이 못 뜬다.
- ★**`/problem-images/` 게이팅이 함께 무력화된다**(`middleware.ts:53-56` 이 세션 쿠키로 막고 있는데
  소비처가 전부 평범한 `<img src>` 라 Authorization 헤더를 못 싣는다). 서명 URL 또는 단수명 쿠키
  병행 중 하나가 **같은 릴리스에** 들어가야 한다 — 안 그러면 무인증 스크래핑이 열린다.
- ★**마크다운 렌더 파이프라인 이전** — remark 4종 + rehype-katex 를 클라이언트로 포팅하거나
  빌드 시 HTML 로 선렌더해 번들한다(링크 재작성은 원리적으로 브라우저에서 못 돈다).

이게 되어야 "웹과 앱이 같은 SPA 코어" 원칙이 성립한다. 안 되면 A 로 가도 두 갈래로 벌어진다.

## 🧾 유지보수 부채 — 1차 출시에 반드시 포함

출시 후에 넣으면 **이미 배포된 앱에는 적용되지 않는다.**

1. **API 버전 스큐 대비** — 사용자는 업데이트를 안 한다. 1년 전 앱이 오늘 서버와 통신한다. API 버전 + 하위호환 규율.
2. **콘텐츠 스키마 버전** — 매니페스트에 스키마 버전. 앱이 감당 가능한 범위만 내려받게.
3. **강제 업데이트 스위치** — 치명적 버그·API 변경 시 "업데이트 필요" 화면.
4. **네이티브 플러그인 최소화** — 플러그인 하나가 영구 부채(OS 업데이트마다 깨짐).
   최소 집합 = 인앱결제 · **Google 로그인(이미 구현됨)** · Apple 로그인 · 보안저장소 · 파일시스템.
   (**카카오는 미구현** — 도입 시 신규 작업. Google OAuth 도 제3자 로그인이라 4.8 을 동일하게 촉발한다.)
   **푸시 알림은 1차 제외 권고**(필수 아님, 나중에 추가 가능).

## 🧯 리뷰로 드러난 누락 (2026-08-13)

전부 **계획에 통째로 없던 것**이다. 상세 근거는 [[app-release-plan-review-2026-08-13]].

### 1. DB 백업이 없다 — 유일하게 되돌릴 수 없는 항목
유료 구독자의 진도·필기·대화가 도커 볼륨 `ms_pgdata` **하나에만** 있다. crontab 의 백업 크론 2건은
`run_db_backup.sh:19` 에서 `-d legal_brain_db` 로 고정 — **math-study 는 대상이 아니다**.
→ `pg_dump -Fc` 야간 크론 + **원격 1부**(R2 또는 tme-laptop) + 30일 로테이션 + 월 1회 복구 리허설.
★사용자 데이터가 **DB 와 R2 로 쪼개지므로 백업은 두 곳을 같은 시점으로 묶는다** — 한쪽만 복구하면
참조 깨진 반쪽 데이터가 된다.

### 2. Google Play 프로덕션 진입 게이트 — 12명 × 연속 14일
2023-11-13 이후 만든 **개인 개발자 계정**은 최소 **12명이 연속 14일** 옵트인한 **비공개** 테스트를
마쳐야 프로덕션 액세스를 신청할 수 있다. **내부 테스트는 인정되지 않는다.**(조직 계정은 면제)
→ 코드로 못 푸는 **2주+ 리드타임**. Phase 2 에서 계정 종류를 먼저 확인하고, 개인 계정이면
테스터 모집을 그때 착수해 리드타임을 임계 경로 밖으로 뺀다.

### 3. 유료 서비스 약관이 없다
월 ₩15,000 을 파는데 `terms.astro` 에 요금·결제·환불 조항이 **0개**다(`privacy.astro:63` 은 이미
"대금결제 기록 5년"을 전제한다). → 이용요금 · 결제수단(스토어 IAP) · 자동갱신 시점 ·
청약철회(전자상거래법 제17조, 디지털콘텐츠 예외) · **환불 주체가 구글·애플이라는 점과 우리 창구** ·
서비스 중단 시 잔여기간 처리 · 쿼터 명시. 연간 요금제를 보류한 사유("중단 시 환불 의무")도 여기서 처리된다.

### 4. 심사자용 계정·지원창구가 없다
전량 유료 + 로그인 필수라 **심사자가 페이월에서 막히면 4.2 방어 논거를 볼 기회조차 없이 반려**된다.
Play 는 로그인 게이팅 앱에 심사용 접근 정보 제공을 의무화한다.
→ 심사용 계정 + **수동 구독 부여 수단**(관리자에서 특정 계정에 구독 상태 주입).
→ 지원 이메일(개인 gmail 아닌 도메인 메일) + 앱 내 「문의하기」 + 개인정보 보호책임자 실명·연락처.

### 5. 장애 알림·크래시 리포팅이 없다
헬스체크는 로그에만 남는다. 앱은 전역 에러 핸들러조차 없다 → "앱이 켜지자마자 죽는다"를
**스토어 별점으로 알게 된다**. → 헬스체크 3연속 실패 시 폰 알림(텔레그램/이메일) · 앱 크래시 리포터
또는 최소한 스택트레이스를 우리 API 로 POST 하는 경로.

## 💳 구독·쿼터 설계

### 쿼터
- **월 3,000턴 + 일 200턴** · **결제일 기준** 리셋(달력 기준은 월말 가입자가 손해)

- 하루 100턴은 빡세게 공부하는 날 걸린다는 판단(사장님) → 200 으로 상향

★쿼터의 목적은 남용 차단이 1차지만, **한도를 꽉 채우면 원가가 수취액의 22-43%** 다 —
  쿼터가 없으면 이 구간이 열린다. 마진 방어 역할도 실재한다.

### 체험
- **스토어 무료체험 7일** · 쿼터는 **유료와 동일(일 200턴)**

  바뀐다 — 그 창에서 한도로 막으면 제품이 별로라고 느끼고 해지한다. **넉넉해야 안 해지한다.**
  꽉 채워 써도 7일에 ₩518, 한 명 전환되면 첫 달에 회수.
- 남용 방지는 쿼터가 아니라 **스토어의 계정당 1회 제한**이 담당한다.

### 자동전환의 윤리 (사장님 우려에 대한 합의)
스토어 체험은 자동전환이 기본 동작이라 그것만 빼는 건 불가능. **도덕성은 자동전환 여부가 아니라
고지 방식에 있다** → 아래를 지키면 떳떳하다.

- 종료 **2일 전 우리도 별도 안내**(애플·구글도 자체 알림을 보낸다)
- 앱 안에 **해지 방법 안내**를 명시적으로 배치

### 구독관리 서비스 (채택)
"제3자가 구독을 관리한다"가 맞되 **범위가 좁다** — PG 와 비슷한 위치.

## 🔄 오프라인 동기화 설계 (확정)

### 원칙 — 상태가 아니라 **이벤트**를 동기화한다
`concept_mastery` · `problem_state` 는 **대체로** 파생 상태다. 정본을 `problem_attempts`(이미 이벤트 로그)로
두고 **서버가 재계산**하면 충돌 해소 로직이 대부분 사라진다.

★**단 그대로는 성립하지 않는다**(2026-08-13 리뷰): 두 테이블에 **attempts 로 환원되지 않는 입력**이 있다 —
`problem-state.ts:67-80` 의 `reset`(행 DELETE)·`mark-mastered`·`skip` 은 attempts 를 만들지 않고 직접
UPSERT/DELETE 하고, `mastery_evidence` 는 `mastery-promote.ts:43` 의 튜터 판단과 가입 시 시드에서만 온다.
그대로 리플레이하면 **지운 상태가 되살아나고 evidence·mark-mastered·skip 이 사라진다** — 통과 조건
"소실 0" 위반. **이 조작들을 먼저 이벤트화한 뒤에야 재계산이 성립한다.**
→ 두 기기가 각각 3건·2건 쌓으면 서버엔 5건이 모이고 mastery 는 그 5건으로 다시 계산된다.

★충돌 해소 코드는 **버그가 조용히 나고, 재현이 어렵고, 데이터가 망가진 뒤 발견**된다. 안 만드는 게 최선.

### 데이터별 성격
| 데이터 | 오프라인 쓰기 | 정본 | 충돌 |
|---|---|---|---|
| **필기** | **핵심** | 기기→서버 병합 | 높음(소실=치명) |
| problem_attempts | 있음 | **이벤트(append)** | 없음 |
| mastery · problem_state | 있음 | **이벤트에서 파생** | 없음(재계산) |
| chat_history | **없음**(튜터는 온라인 전용) | 서버 | 없음 |

### 전송 방식 — 커서 기반 델타
서버가 **사용자별 단조 증가 seq** 부여. 기기는 `last_synced_seq` 보관.
`① 로컬 미전송 push → 서버가 seq 부여` → `② GET /sync?since=seq 로 pull`.
★**기기 시각을 순서 기준으로 쓰지 않는다**(사용자가 시계를 바꾼다). 시각은 표시용.

### 필기 병합 — 획 id + 삭제 tombstone 합집합
```
문서 = { v:3, layers:[{id, name, visible, deleted?}],
         strokes:{ layerId:[{id, ...}] }, deletedStrokes:[id] }
병합 = strokes 합집합 − deletedStrokes 합집합 (레이어도 tombstone 포함)
```
★실제 포맷이 **레이어 구조**(`InkCanvas.tsx:145` `{v:2, layers, strokes}`)라 단순 배열 모델로는 안 된다.
레이어 간 stroke 이동(`InkCanvas.tsx:16` move)은 삭제+추가로 표현한다.
tombstone 이 없으면 "원래 없던 획"과 "지운 획"을 구별 못 해 **지운 게 되살아난다**.
별도 이벤트 테이블 없이 문서 안에서 해결 → 테이블을 안 늘린다.
★**실패 모드 원칙: 소실보다 중복이 낫다.** 겹쳐 보이면 학생이 지우면 되지만, 한쪽을 버리면 복구 불가.

### 초기 동기화
| 데이터 | 방식 |
|---|---|
| 진도·mastery·이벤트 | **즉시 전량**(수십 KB) |
| **필기·튜터 이미지** | **열 때 그 문서만(lazy)** + "이 회차 오프라인 저장" 버튼 |

로그인 직후 전량 다운로드는 금지 — 폰에서 5분 대기는 그 자체가 이탈 사유.

### 동기화 시점
앱 시작·포그라운드 복귀(push+pull) · 네트워크 복구(push) · **필기 화면 이탈 시(push 필수)** · 5분 주기.
**실시간(웹소켓)은 넣지 않는다** — 두 기기 동시 사용 시나리오가 없고 유지보수 부담만 크다.

### 갇힌 데이터는 투명성으로
오프라인 기기 안의 데이터는 **물리적으로 전송 불가**. 대신 `⟳ 마지막 동기화 3시간 전 · 미전송 12건` 을
노출한다. 이 표시 유무가 "CS 문의"와 "아 태블릿을 안 켰구나"를 가른다.

### ★저장 위치 — 사용자 클라우드(구글 드라이브)는 **미채택**
전제 검증 결과 **필기 저장은 사실상 공짜**였다(획 120×점 60 문서가 **gzip 후 2.3KB**, 125배 압축):
| 규모 | 용량 | 월 비용 |
|---|---|---|
| 학생 1,000명 × 문제 200개 | 0.4GB | **₩9** |
| 학생 10,000명 × 문제 500개 | 10.9GB | **₩221** |

드라이브를 쓰면 비용이 아니라 다른 걸 지불한다 — ①**서버가 병합 불가**(기기 병합 강제, 드라이브가
자체 충돌사본 생성) ②**디버깅 불가**(사용자 드라이브를 볼 수 없다 = 고칠 수 없는 버그 카테고리 신설.
GoodNotes iCloud 동기화 불만의 정체) ③가입 직후 OAuth 추가(이탈) ④사용자 용량·권한 사정에 종속
⑤iOS 학생의 구글 계정 마찰.
→ **자체 오브젝트 스토리지 + 압축 + 내보내기 기능**으로 간다. 데이터 소유권 메시지는 **내보내기**로 지킨다.

**필수 최적화**: gzip · 좌표 반올림(소수 2자리) · 점 솎기. DB 엔 메타(seq·크기·수정시각)만, **본문은 스토리지**.

## 🖼 튜터 첨부 이미지 (확정)

### 발견된 문제 둘
**① 이미지가 대화 DB 에 base64 로 들어가 있다** — `chat_history.messages` jsonb 에 data URL 통째로.
실측: 삼각비 대화 **568KB**, 분수_변환 254KB. **학생 1,000명 필기 전체(0.4GB)보다 대화 하나가 무겁다.**
2MB 상한이 있어 **사진 3-4장이면 대화 저장이 통째로 실패(413)**.

**② 이미지가 다음 턴에 사라진다** — `formatHistory` 가 `m.content`(텍스트)만 넘긴다.
```
학생: [손풀이 사진] 이거 봐줘        → 튜터: 3번째 줄 부호가 틀렸어요
학생: 그럼 거기부터 다시 하면?      → 튜터: (사진 못 봄) 어떤 문제인지 다시…
```
**필기 채점이 코어인데 후속 질문에서 무너진다.**

### 결정
1. **오브젝트 스토리지로 분리** — 대화엔 참조(`imageRefs`)만. 필기와 같은 원칙.
2. **업로드 전 리사이즈·WebP** — 긴 변 1,600px(손글씨 판독에 충분). 2-8MB → 150-300KB.
   단 **LLM 전송은 타일 원칙(D17) 유지** — 현재 클라이언트의 비전타일/표시통이미지 분리 구조는 그대로.
3. **이미지 유지 = 최근 1-2턴 + 전사 요약 병행.** 첫 턴에 튜터가 이미지를 전사·요약해 히스토리에 남기면,
   그 뒤로는 이미지 없이 맥락이 이어진다. **luna 판독 충실도 10.0/10·오독 0** 실측이라 전사를 믿을 만하다.
   (전 대화 이미지 유지는 비용 폭증 — 이미지는 캐시가 잘 안 걸린다.)
4. **보관 90일** — 이후 이미지 삭제, 전사 텍스트만 유지. 학생 손글씨·미성년자 가능성 때문에 무기한 보관은 위험.
   탈퇴 시 **스토리지 파일까지** 삭제되는지 확인 필요(DB 는 CASCADE 지만 스토리지는 별도).
5. 동기화는 필기와 동일 — 참조는 즉시, 실물은 lazy.

### 기존 데이터 마이그레이션
대상 3건(2026-06-11 · 06-29 ×2, 568/254/65KB). **스토리지 구축 이후** 실행.
★세 건 모두 6월 것이라 90일 규칙을 그대로 적용하면 **마이그레이션 직후 삭제 대상**이 된다
→ 레거시는 **마이그레이션일 기준**으로 보관 기간을 재시작하거나, 사장님 본인 데이터이므로 예외 처리.

표본 40장 실측:
| 형식 | 비율 | 전체 404MB 환산 |
|---|---|---|
| 원본 PNG | 100% | 404MB |
| PNG 최적화 | 99.6% | 402MB (무의미) |
| **WebP 무손실** | **33.9%** | **약 137MB** |
| WebP q88(손실) | 35.0% | 141MB |

→ **무손실을 택한다.** 손실과 크기가 같은데 수식·첨자를 손상시킬 이유가 없다.
**웹도 함께 전환**한다(웹 로딩도 3배 빨라짐 — 앱과 무관하게 이득).

### 전체 콘텐츠: 약 425MB → 약 145MB
| 항목 | 현재 | 최적화 후 |
|---|---|---|
| 문제 이미지 5,728장 | 404MB | **약 137MB** |
| 문제 md | 12.9MB | 2.4MB (gzip) |
| 풀이 캐시 | 2.5MB | 1.0MB |
| 개념 md | 3.9MB | 0.9MB |
| 위젯 | 5.6MB | ~1MB |

### 배포 방식 — **(B) 텍스트 번들 + 이미지 회차 단위 다운로드**
- **텍스트 약 4.3MB(gzip) 는 앱에 번들** — 개념·문제·풀이·위젯. ★번들 형태(md vs 선렌더 HTML)는
  Phase 3 의 마크다운 파이프라인 결정과 함께 정한다(선렌더 HTML 은 KaTeX 마크업 때문에 더 커진다)
- **이미지만 다운로드**, 단위는 **회차**(116개 회차 · WebP 후 **회차당 평균 약 1.2MB**)
- 기준: **변하는 것만 네트워크로 뺀다.** 개념·위젯·풀이는 거의 안 바뀌지만 문제 이미지는
  새 회차마다 늘어난다. 텍스트 수정은 앱 업데이트로 충분

### 버전 관리 — 매니페스트 + 내용 주소
파일명에 해시를 넣는다 → **캐시 무효화 문제가 원천 소멸**(내용이 바뀌면 이름이 바뀐다).
앱은 매니페스트를 받아 **로컬에 없는 해시만** 내려받는다. 매니페스트에 **스키마 버전** 포함
(구버전 앱이 감당 못 하는 형식은 무시하게).

### 인증 — 전체 유료라 다운로드도 막아야 한다
공개 URL 이면 비구독자가 데이터셋을 통째로 긁는다. 기출 문제 자체는 공개 자료지만
**정리된 데이터셋과 풀이가 제품의 실체**다. → 구독 확인 후 **서명된 임시 URL** 발급.
(번들되는 텍스트는 추출 가능하지만 어느 앱이나 마찬가지 — **증분되는 이미지만 보호**해도 실효 충분.)

## 🌩 Cloudflare 활용 (확정) — 이미 쓰는 계정을 그대로

포렌식 프로젝트가 이미 **Tunnel · Pages · Pages Functions** 를 쓰고 있다(같은 tme 서버).
버킷·터널·프로젝트 **이름을 분리**해 계정만 공유한다.

| 구성 | math-study 용도 |
|---|---|
| **R2** | 콘텐츠 이미지 54MB · 필기 문서 · 튜터 첨부 이미지. **전송료 0원**(무료 한도: 저장 10GB · Class A 100만/월 — 우리는 한참 안쪽) |
| **Tunnel + 도메인** | tme API 를 고정 주소·**TLS 자동**으로 노출. 포트 개방·고정IP 불필요 → 미결이던 `MS_SECURE_COOKIES=true` 가 여기서 풀린다. ★포렌식의 `--url` 임시터널(주소 매번 변경)이 아니라 **네임드 터널**로 — 앱은 주소가 바뀌면 안 된다 |
| **Workers** | 구독 확인 → **R2 서명 URL 발급**. tme 를 거치지 않으니 서버 부하 0 |
| **Pages** | SPA 배포. 웹 서빙이 tme 에서 떨어져 나가고 **tme 는 API 만** 담당 |

```
[앱 / 웹]
   ├─ 정적 SPA            → Cloudflare Pages
   ├─ 콘텐츠 이미지        → R2 (Worker 가 서명 URL 발급)
   └─ API(인증·튜터·동기화) → Tunnel → tme
```
→ **tme 가 받는 건 API 호출뿐.** "서버 역할 최소화" 목표에 정확히 부합한다.

### 실행 항목
- **WebP 변환 파이프라인** — 인제스트에 변환 단계 추가 + 기존 5,728장 일괄 변환
- R2 버킷 생성 · 네임드 터널 · 도메인 연결
- 스토리지 구축 후: **chat_history 이미지 3건 마이그레이션**

## 🗓 실행 계획 — **날짜 없이 관문(exit criteria)으로만**

완성도 우선이므로 "몇 개월"이 아니라 **"무엇이 되면 다음"** 으로 잡는다. 날짜를 박으면 관문을 건너뛴다.

| Phase | 내용 | **통과 조건** |
|---|---|---|
| **0** | **지금 웹에서도 문제인 것** — 튜터 이미지가 다음 턴에 사라짐 · chat_history jsonb 비대화(1건 568KB) · WebP 전환(**서빙 계층 매핑까지만**) · ★**DB 백업 크론** | 손풀이 사진 후속 3턴 맥락 유지 · 대화 jsonb 정상화 · WebP 서빙 · **야간 덤프 + 원격 1부 + 복구 리허설 통과** |
| **2** | ★**빈 껍데기 앱 조기 업로드** + **Play 계정 종류 확인 · 비공개 테스트 트랙 개설 · 테스터 12명 모집 착수** | 기능 0 인 앱이 내부테스트 트랙 업로드 + 실기기 구동 · 계정 종류 확정 |
| **3** | **SSR 제거 → SPA + JSON API** · 세션쿠키→토큰 | 웹이 SPA 로 완전 동작 · 기존 기능 회귀 0 |
| **4** | 데이터 재설계 — 이벤트 정본화 · 획 id+tombstone · seq 델타 동기화 | 두 기기 오프라인 작업 합류 시 **소실 0** |
| **5** | 인프라 — R2 · 네임드터널+도메인 · Workers 서명URL · Pages · 매니페스트 · **DB 백업** | **미인증** 다운로드 차단(서명 URL 발급에 유효 토큰 필요) · 오프라인 문제 열람 · **빈 DB 에 덤프 복원 후 로그인·필기 로드 확인** · **헬스체크 3연속 실패 시 폰으로 알림 도착** (여기서 `MS_SECURE_COOKIES=true` 도 켜짐) |
| **6-전 관문** | **필기 지연 판정** (실기기 펜) | "출시 가능"(A 유지) 또는 "네이티브 필요"(D 추가) |
| **6** | 앱 셸 — Capacitor 8 · 플러그인 최소집합 · **강제업데이트 스위치 · API 버전 규율** | 앱에서 로그인→열람→필기→튜터 끝까지 동작 |
| **7** | 결제 — 구독관리 서비스 · 상품등록 · **프록시 게이팅** · 구매복원 | 비구독자가 튜터 못 씀 · **비구독자 콘텐츠 다운로드 차단** · 체험 7일 자동전환 · 쿼터 경고→차단 |
| **8** | 심사 — 스토어 자산 · Data safety · 14세미만 · 국외이전 · 법무 · **유료약관** · **심사용 계정** · **지원창구** | **비공개 테스트 14일 완주 + 프로덕션 액세스 승인** → 프로덕션 |

### 임계 경로
```
Phase 3(SSR 제거·최대 공사) → Phase 5(인프라) → Phase 6(앱 셸) → 7(결제) → 8(심사)
```
Phase 0·2·4 는 **병렬 가능**. ★**Phase 5 는 병렬이 아니다**(2026-08-13 리뷰 정정) —
Pages 가 배포할 SPA 자체가 Phase 3 산출물이고, **호스트를 쪼개는 순간 동일출처 CSRF 검사가
모든 쓰기 요청을 403 으로 막는다**(`middleware.ts:83-88` · `auth.ts:124-141`).

★**필기 판정은 임계 경로의 출발점이 아니다**(2026-08-13 정정). 의존 관계를 다시 보니
Phase 0·2·3·4·5 는 **판정 결과와 무관하게 동일**하다 — 획 id 는 네이티브로 가도 그대로 쓰고,
SSR 제거·인프라는 어느 안이든 필요하다. **갈리는 건 Phase 6 하나**(필기 화면을 WebView 로 둘지
네이티브 뷰로 뺄지) → 관문을 Phase 6 직전으로 옮겼다. 태블릿 확보를 기다리며 다른 Phase 를 진행한다.

### ★Phase 2 를 일찍 하는 이유
**업로드 실패는 가장 늦게 드러나는 실패다.** 포렌식은 targetSdk 34 로 전부 만들어놓고
업로드에서 막혔다. 우리는 **아무것도 안 만든 상태에서** 서명키·AAB·업로드 파이프라인을 검증한다.
내부 테스트 트랙은 **공개 스토어 페이지를 만들지 않으므로**(포렌식 실측) 부담이 없다.

### 필기 지연 판정 — 진행 상황 (2026-08-13)

**맥북 트랙패드로 시험 → "좋다"(사장님).** 다만 **이 결과로는 판정할 수 없다.**

펜 지연이 문제가 되는 이유는 **펜촉과 그려지는 선 사이의 간격이 눈에 보이기 때문**인데,
트랙패드는 화면에 펜촉이 없어 **비교할 기준점 자체가 없다** → 어떤 지연이어도 "좋다"가 나온다.
즉 이 테스트는 **통과할 수밖에 없는 테스트**다. 그 외에 필압·팜리젝션·고빈도 입력(120-240Hz)도 검증 불가.

| 검증 항목 | 트랙패드 | 펜 |
|---|---|---|
| 지연 체감 | **불가**(기준점 없음) | 핵심 |
| 필압 | 없음 | 굵기 표현 |
| 팜리젝션 | 불필요 | 손바닥 접촉 |

**상태**: 아이패드는 집에 있어 당장 불가 → **Phase 6 직전까지 보류**. 그 전에 아이패드+펜슬 또는
갤럭시 탭+S펜으로 판정한다.

★이미 있는 증거: `InkCanvas` 에 **실기기에서 잡은 픽스가 박혀 있다**(안드로이드 Chrome 검정
오버레이 승격, iOS 다중 desync 레이어 합성 실패) — 누군가 펜으로 써보고 발견한 버그들이다.
완전 미검증이 아니라 **"쓸 만한가"의 최종 판단만 남은 상태**.

### 일정을 흔들 수 있는 것
1. **필기 지연 미달** → D안(필기 네이티브) 추가, 브리지 설계 발생
2. **SSR 제거가 예상보다 큼** → 사용자 대면 25개 페이지의 상태·인증 의존이 얽혀 있으면 증가
3. **심사 반려** → 4.2(최소기능)가 주 위험. 오프라인·펜·결제가 **다 들어간 뒤** 제출한다

### Phase 3 의 고유 위험 — 살아있는 서비스를 고친다
사장님이 매일 쓰는 웹이 이전 과정에서 깨질 수 있다. **페이지 단위 점진 이전**으로 가고
각 단계마다 웹이 도는지 확인한다. **45개를 한 번에 뒤집지 않는다.**

> 상태: Phase 0 **미착수**(사장님 지시로 대기). 회의 종료 시점에 코드 변경 없음.
