# 📱 앱 출시 설계 — 회의록 (진행 중)

> 분류: Wiki / 아키텍처. **회의 모드 산출물** — 결정된 것만 적고, 미결은 '미결'로 남긴다.
> 코드 변경은 결정이 끝난 항목부터 별도로 진행한다.

## 🎯 목표

수능 수학 학습 서비스를 **Android·iOS 앱으로 출시**한다. 지금은 웹으로 서빙 중.
사장님 방침: **필요한 내용은 최대한 앱에 담고, 서버 역할은 최소화**한다.
우선순위는 **속도가 아니라 완성도와 유지보수 용이성**.

| 크레딧 추가구매 | **출시 제외** — 한도 도달자가 유의미하게 나오면 그때 |

| 출시 순서 | **Android 먼저**, iOS 요건은 처음부터 설계에 반영 |

## 📊 판단 근거 (실측)

### 콘텐츠 규모 — 약 210MB
| 항목 | 크기 |
|---|---|
| 문제 이미지 | 160MB (5,728장) |
| 문제 md | 19MB |
| 풀이 캐시 | 17MB |
| 개념 md | 6.8MB |
| 위젯 | 5.6MB |

→ 전량 번들은 비현실적(초기 다운로드 + **콘텐츠 갱신마다 앱 심사**). **얇은 앱 + 콘텐츠 동기화**로 간다.

### 재작성하면 버리는 웹 자산
컴포넌트 **11,999줄** · Astro 페이지 45개 · API 23개.
무거운 축이 전부 웹 렌더링에 묶여 있다 — `Geometry`(1,087) · `Graph`(1,130) · `Geometry3D`(754, three.js)
· `InkCanvas`(615) · `ChatPanel`(567). 웹 전용 의존성 = katex · mathjs · function-plot · three · remark-math.

### 필기 캔버스는 이미 웹 저지연 스택
`desynchronized` 컨텍스트 · `getCoalescedEvents` · `getPredictedEvents` · 진행 overlay 분리 · 압력 · 팜리젝션.
**실기기에서 잡은 픽스가 코드에 박혀 있다**(안드로이드 Chrome 검정 오버레이 승격, iOS 다중 desync 레이어
합성 실패 등). 네이티브 재작성은 이 부류의 버그를 처음부터 다시 만나는 일 → **검증된 자산을 먼저 쓴다.**

### 스택 비교 (유지보수 기준 = 평생 유지할 코드베이스 수)
| 안 | 코드베이스 | 버그 1건 수정 비용 |
|---|---|---|
| **A. Capacitor** | 웹 1 (+얇은 셸) | **1회** |
| **D. A + 필기 네이티브** | 웹 1 + 작은 네이티브 2 | 1회(필기만 3회) |
| B. React Native | 웹 1 + RN 1 (+수식용 WebView) | **2회** |
| C. 완전 네이티브 | 웹 1 + iOS + Android | **3회** |

B 가 최악 — 수식·도형·3D 를 RN 네이티브로 못 만들어 결국 WebView 를 끼우게 되므로 **WebView 버그는
그대로 안으면서 코드베이스만 하나 늘어난다.**

### 단가 구조 — 학생 1명당 월 (스토어 15%, LLM 평균 600턴 가정)
| 항목 | 금액 |
|---|---|
| 소비자 결제 | ₩15,000 |
| 부가세 10% | −₩1,364 |
| 스토어 수수료 15% | −₩2,045 |
| 구독관리 서비스 1% | −₩150 (월매출 약 ₩3.4M 미만은 **무료**) |
| LLM (평균 600턴) | −₩222 |
| **남는 돈** | **약 ₩11,219 (75%)** |

한도를 꽉 채워도(3,000턴 = ₩1,110) 남는 돈 ₩10,331 · 69%.

### 규모별 (월)
| | 100명 | 500명 | 1,000명 | 5,000명 |
|---|---|---|---|---|
| 총 매출 | ₩1.5M | ₩7.5M | ₩15M | ₩75M |
| 순이익 | ₩1.09M | ₩5.53M | ₩11.1M | ₩55.9M |

★**마진이 규모와 거의 무관**하다(원가 대부분이 매출 비례). 작은 규모에서도 건강하다.

  남은 레버는 수수료뿐인데 소규모 프로그램 15% 가 이미 최선.

## ⚠️ "서버는 로그인만" 이 성립하지 않는 이유

| 서버 역할 | 뺄 수 있나 | 이유 |
|---|---|---|
| 인증·회원관리 | 불가 | 원래 계획 |
| **LLM 프록시** | **불가** | 키를 앱에 넣으면 **바이너리에서 추출**된다 → 남의 크레딧으로 무단 사용. 사용량 계측·쿼터·차단도 서버에만 있다 |
| **구독 상태 검증** | **불가** | 클라이언트 판단은 위조 가능. 단 **구독관리 서비스(RevenueCat 류)로 대부분 외주 가능** |
| 콘텐츠 배포 | 가능 | CDN·오브젝트 스토리지로 이전 |
| 사용자 데이터 동기화 | 가능하나 **유지 결정** | 빼면 기기 변경 시 진도 소실 |

★**서버 역할을 줄여도 서버 비용은 거의 안 준다.** 비용을 정하는 건 기능 개수가 아니라 **가동 요건과
콘텐츠 트래픽**이다. 프록시는 I/O 대기라 CPU 를 거의 안 쓴다 → 작은 VPS 하나로 충분.
현재 tme 자가호스팅은 한계비용 0 이지만 **상용으로는 단일 장애점**.

## 🔨 스택과 무관하게 반드시 해야 하는 공사

**SSR 제거 → 클라이언트 렌더링 + JSON API.** 앱 프로젝트의 절반 이상을 차지한다.
- 페이지 45개 렌더링을 클라이언트로 이동
- 인증 게이팅을 서버 미들웨어 → 앱 라우팅으로 이동
- 콘텐츠 조회를 서버 → **로컬 캐시**로 전환
- 세션 쿠키 → **access/refresh 토큰**(네이티브는 쿠키가 불편, Keychain/Keystore 보관)

이게 되어야 "웹과 앱이 같은 SPA 코어" 원칙이 성립한다. 안 되면 A 로 가도 두 갈래로 벌어진다.

## 🧾 유지보수 부채 — 1차 출시에 반드시 포함

출시 후에 넣으면 **이미 배포된 앱에는 적용되지 않는다.**

1. **API 버전 스큐 대비** — 사용자는 업데이트를 안 한다. 1년 전 앱이 오늘 서버와 통신한다. API 버전 + 하위호환 규율.
2. **콘텐츠 스키마 버전** — 매니페스트에 스키마 버전. 앱이 감당 가능한 범위만 내려받게.
3. **강제 업데이트 스위치** — 치명적 버그·API 변경 시 "업데이트 필요" 화면.
4. **네이티브 플러그인 최소화** — 플러그인 하나가 영구 부채(OS 업데이트마다 깨짐).
   최소 집합 = 인앱결제 · 카카오 SDK · Apple 로그인 · 보안저장소 · 파일시스템.
   **푸시 알림은 1차 제외 권고**(필수 아님, 나중에 추가 가능).

## 🚧 심사·법무 체크리스트

- **Sign in with Apple** — 카카오 등 제3자 로그인을 제공하면 애플이 동등 옵션을 요구(4.8). 처음부터 포함 전제.
- **앱 내 회원탈퇴** — 계정 생성이 가능하면 필수(5.1.1(v)). math-study 엔 이미 탈퇴 구현됨 → 앱에 노출만.
- **가이드라인 4.2(최소 기능)** — 순수 WebView 래퍼는 반려 위험. 방어 = **오프라인 콘텐츠 + 펜 입력 + 인앱결제**.
- **만 14세 미만 법정대리인 동의** — 중1~중3 콘텐츠가 있어 실제로 온다. 카카오 `age_range` 로 분기 가능.
- **손풀이 이미지의 국외 이전** — 해외 LLM API 로 나간다. PIPA 고지·동의, 미성년자 건은 더 엄격. **법무 검토 항목**.

## 💳 구독·쿼터 설계

### 쿼터
- **월 3,000턴 + 일 200턴** · **결제일 기준** 리셋(달력 기준은 월말 가입자가 손해)
- 80% 도달 시 경고 → 100% 하드스톱. **예고 없이 막히는 게 제일 나쁘다**
- 일 200턴 = 폭주 차단, 월 3,000턴 = 실제 예산 상한. "몰아서 쓰되 월 총량은 지킨다"
- 하루 100턴은 빡세게 공부하는 날 걸린다는 판단(사장님) → 200 으로 상향

★쿼터의 목적은 **마진 방어가 아니라 남용 차단**이다. 한도를 꽉 채워도 원가는 수취액의 9.6%.

### 체험
- **스토어 무료체험 7일** · 쿼터는 **유료와 동일(일 200턴)**
- ★체험 쿼터를 조이면 **역효과**다. 자동전환이 붙으면 학생의 결정은 "살까?"가 아니라 **"해지할까?"** 로
  바뀐다 — 그 창에서 한도로 막으면 제품이 별로라고 느끼고 해지한다. **넉넉해야 안 해지한다.**
  꽉 채워 써도 7일에 ₩518, 한 명 전환되면 첫 달에 회수.
- 남용 방지는 쿼터가 아니라 **스토어의 계정당 1회 제한**이 담당한다.

### 자동전환의 윤리 (사장님 우려에 대한 합의)
스토어 체험은 자동전환이 기본 동작이라 그것만 빼는 건 불가능. **도덕성은 자동전환 여부가 아니라
고지 방식에 있다** → 아래를 지키면 떳떳하다.
- 시작 화면에 **"7일 뒤 월 15,000원 결제, 언제든 해지 가능"** 을 크게
- 종료 **2일 전 우리도 별도 안내**(애플·구글도 자체 알림을 보낸다)
- 앱 안에 **해지 방법 안내**를 명시적으로 배치

### 구독관리 서비스 (채택)
"제3자가 구독을 관리한다"가 맞되 **범위가 좁다** — PG 와 비슷한 위치.
| 누가 | 무엇을 |
|---|---|
| 구글·애플 | 결제 수납·갱신·정산 (**돈은 여기 있다**) |
| 구독관리 서비스 | "누가 언제까지 구독 중인가" **상태 정보만** 추적·정규화 |
| 우리 | 상태를 받아 기능을 열어줌. **고객 관계는 우리 것** |

→ 서비스가 사라져도 **구독 자체는 스토어에 살아 있다.** 소유자가 아니라 통역사.

**락인·장애 완화: 권한 상태를 우리 DB 에 미러링**한다. 웹훅으로 `subscription_status` 를 갱신해두면
평시엔 서비스가 정본, 장애 시엔 우리 캐시가 버틴다. 이 미러링이 곧 **탈출구**이기도 하다
(떠날 때 "웹훅 소스 교체"로 끝난다).

**직접 구현 대비 절감**: Play Developer API 연동 + GCP Pub/Sub 구축 + 상태기계 + 복원/환불 처리,
그리고 **iOS 추가 시 애플 스택 전부 재구현**, 매년 오는 결제 API 변경 대응(애플 verifyReceipt 폐기,
구글 Play Billing 버전 마감 강제 — 미준수 시 앱 내려감).

## ❓ 미결 안건

1. **콘텐츠 배포 설계** — 210MB 분할·버전관리·재개 가능 다운로드, 스토리지 선택(egress 무료 우선)
2. **오프라인 동기화 규칙** — 로컬/서버 충돌 해소, 무엇을 로컬 정본으로 둘지
3. **필기 지연 기준선** — 현재 웹 캔버스를 실기기에서 평가해 D 전환 기준을 수치로 확정
   ★다른 결정의 선행 조건. 미정이면 "역시 네이티브였나" 재검토가 반복된다
4. **호스팅** — tme 자가호스팅 유지 vs 클라우드 이전(단일 장애점 해소)
5. **출시 일정** — 완성도 우선이므로 역산이 아니라 마일스톤 기준으로
6. **쿼터 계측 지점** — `tutor_usage` 는 이미 있음. 프록시에서 **구독+쿼터를 함께 게이팅**해야 실효.
   결제를 붙여도 프록시가 권한을 안 보면 무료 사용자가 튜터를 그대로 쓴다
